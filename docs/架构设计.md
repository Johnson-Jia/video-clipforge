# 架构设计

ClipForge 是一个由 DAG 编排的视频制作管线。本文档涵盖核心架构决策以及各组件如何协同工作。

## DAG 编排

### Schema 即唯一真相源

所有 artifact 定义都存放在 [`schema.yaml`](../.claude/commands/clipforge/schema.yaml) 中。Schema 定义了：

- **`generates`** — 证明 artifact 完成的文件模式（如 `**/output.mp4` 的 glob 模式）
- **`requires`** — 硬依赖（必须在此 artifact 开始之前完成）
- **`requires_any`** — 条件依赖（当条件 artifact 执行时变为硬依赖）
- **`optional`** — 可选 artifact（跳过时不阻塞下游）
- **`condition`** — 条件阶段的触发条件

这是唯一声明依赖的地方。Stage 文件和定时任务文件引用 Schema，但从不重复声明依赖。

### 依赖图

```
env-check → content → design ─┬→ narration → audio ──┬→ video → delivery → cleanup
                               │                assets ┘
                               └→ assets
                                                  narration → movie-clips（条件触发）
```

### 状态检测

状态 = 文件存在性。系统检查 `generates` 的 glob 模式是否匹配磁盘上的实际文件。没有数据库、没有状态 API、没有状态机。

- 如果 `design.md` 存在 → design artifact 完成
- 如果 `output.mp4` 和 `output_no_bgm.mp4` 都存在 → video artifact 完成
- 如果 `final.mp4` 和 `final_no_bgm.mp4` 和 `cover.png` 和 `douyin.md` 都存在 → delivery artifact 完成

这意味着你可以通过手动创建输出文件来跳过某些阶段（调试或恢复中断的运行时有用）。

## 阶段管线

### Stage 文件

每个阶段是一个自包含的技能文件（`.claude/commands/clipforge/stageN-xxx.md`），包含：

1. **CSO 描述** — 何时触发此阶段（不是做什么）
2. **执行步骤** — 读什么、做什么、写什么
3. **反合理化表** — 此阶段特定的 Red Flags 和 Common Rationalizations
4. **完成标准** — 结束时必须存在哪些文件

### 共享规则

跨领域的公共规范存放在共享文件中：

| 文件 | 内容 | 使用方 |
|------|------|--------|
| `_shared-rules.md` | 内容规范、语言规则、黄金 3 秒规则、URL 禁令 | Stage 1、3、6、7 |
| `_cleanup-rules.md` | 文件保留/删除规则 | cleanup |
| `_cron-renew.md` | 定时任务自续期协议 | 所有定时任务文件 |
| `_movie-clips.md` | 电影片段提取 | narration 和 audio 之间的条件阶段 |
| `_bgm-pixabay.md` | BGM 下载辅助工具 | audio 阶段 |

## 执行模式

### 交互模式

用户在 Claude Code 中调用 `/clipforge`。控制器：
1. 读取 `schema.yaml` 并解析 DAG
2. 扫描已完成的 artifact（通过文件存在性）
3. 对剩余 artifact 进行拓扑排序
4. 依次执行每个就绪的 artifact，展示结果并请求确认
5. 每次完成后重新扫描

### 自动化模式（定时任务）

定时任务文件（如 `github-daily-trending.md`）批量调度 SubAgent：

| 批次 | Artifact | 原因 |
|------|----------|------|
| SubAgent-1 | env-check → content → design → narration | 顺序执行，无并行机会 |
| SubAgent-2 | audio | 依赖 narration |
| SubAgent-3 | video | 依赖 audio |
| SubAgent-4 | delivery → cleanup | 顺序完成最终步骤 |

每个 SubAgent 以全新的上下文窗口启动。SubAgent 的 prompt 包含：
1. 项目上下文（目录、模式、内容类型）
2. 需要读取和执行的 stage 文件
3. 完成标准（需要验证的文件）

SubAgent 之间通过文件系统传递状态 — SubAgent-2 读取 SubAgent-1 写入的 `narration_segments.json`。

## 音频架构

### 分段 TTS

旁白按场景拆分为多个片段。每个片段独立通过 `edge-tts` 生成 TTS，产出单独的 MP3 文件。时长记录在 `segment_durations.json` 中。

这解决了音画同步问题：HTML 中每个场景的时长匹配其实际旁白时长，而非估算值。

### 内嵌音频

旁白和 BGM 通过 `<audio>` 元素直接嵌入 HTML：

```html
<audio id="narration" src="narration.mp3"></audio>
<audio id="bgm" src="bgm.wav" data-volume="0.08"></audio>
```

HyperFrames 在渲染期间读取这些元素并原生混音到输出的 MP4 中。无需 FFmpeg 后处理。

### BGM 音量

BGM 音量按片段分析（旁白响度各不相同）。`segment_durations.json` 文件包含 `meta.bgm_volume`，video 阶段读取该值来设置 BGM 音频元素的 `data-volume`。

## 错误恢复

DAG 结构支持最小范围的回滚：

| 问题 | 回滚到 | 级联影响 |
|------|--------|----------|
| 旁白时间偏差 1-3 秒 | 仅 video | 调整 `data-duration`，重新渲染 |
| 旁白时间偏差 >3 秒 | narration | narration → audio → video → delivery |
| 视觉风格不匹配 | design | design → assets → video |
| BGM 情绪不匹配 | audio | audio → video |
| 内容错误 | narration | narration → audio → video → delivery |

**原则：** 回滚到必须更改的最小阶段。DAG 决定了级联范围。

## 设计决策

### 为什么用 schema.yaml 而不是代码？

Schema 是声明式契约。交互控制器和定时任务文件都读取它来理解依赖关系。如果用代码编写，定时任务文件无法在不导入模块的情况下复用这些逻辑 — 而 Claude Code 技能没有模块系统。

### 为什么用文件状态而不是数据库？

简单且可调试。你可以通过 `ls` 检查项目状态。你可以通过检查哪些文件存在来恢复失败的运行。无外部依赖。

### 为什么用 SubAgent 而不是一次性执行到底？

上下文窗口限制。完整的视频制作流程涉及读取内容、编写旁白、运行 TTS、组合 HTML 和渲染。这超出了单个上下文窗口的容量。SubAgent 隔离每个批次，让每个窗口保持聚焦。

### 为什么用内嵌音频而不是 FFmpeg 混音？

HyperFrames 在渲染期间提供原生音频混音。增加 FFmpeg 作为后处理步骤是多余且容易出错的。`<audio>` 元素方案更简单、更易维护，且效果更好（帧精确同步）。

## 分类系统

### 架构

ClipForge 使用**分类配置文件**模式，将通用管线逻辑与内容特定规则分离：

```
categories/
├── _category-schema.md   # 格式规范
├── github.md             # GitHub 开源项目
├── comics.md             # 漫画（未来）
└── novel.md              # 小说（未来）
```

每个分类文件为特定阶段定义覆盖规则：

| 阶段 | 可覆盖内容 |
|------|-----------|
| content | 数据源、选择策略、深度调研方法、回退方案 |
| design | 默认风格方向、色彩偏好 |
| narration | Hook 模板、特殊规则、字数范围 |
| audio | 默认音色、语速 |
| delivery | 标签、评论模板、封面标记 |
| shared-rules | 数据验证规则 |

### 为什么用分类配置文件而不是独立管线？

一个通用管线配合可插拔的分类配置，优于多个独立管线：

1. **共享基础设施** — DAG 编排、SubAgent 调度、音频混音、渲染和清理在所有分类间完全相同。无重复。
2. **覆盖而非替换** — 分类只声明差异项。通用 stage 文件提供合理的默认值。新增分类只需一个新配置文件。
3. **品质一致** — 反合理化表、黄金 3 秒规则和渲染安全规则对所有分类统一适用。
